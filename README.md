# Heatnet — сервис моделирования трасс подключения к тепловым сетям

Решение конкурсного кейса «Лидеры цифровой трансформации» 2026: сервис принимает
GeoJSON с существующей тепловой сетью, камерами, точками подключения перспективных
ОКС и пространственными ограничениями, автоматически строит до трёх содержательно
различающихся вариантов новой сети и выгружает результат в GeoJSON по разделу 7
технического приложения.

**Живой стенд:** <https://heatnet.85-198-82-32.nip.io> — сервис можно попробовать
из браузера без установки (веб-интерфейс, Swagger UI, интерактивный
[разбор алгоритма](https://heatnet.85-198-82-32.nip.io/ui/algorithm.html)).

## Стек (по требованиям ТЗ, п. 3.2)

## Быстрый старт

### Docker (рекомендуется, Ubuntu Server 22)

```bash
docker-compose up --build -d
# Swagger UI: http://localhost:8080/swagger-ui.html
# Веб-интерфейс: http://localhost:8080/ui/
```

Для проверки без конкурсных данных в репозитории лежит синтетический
пример входных данных — `samples/sample-city.geojson` (25 кварталов,
12 точек подключения, река, ж/д, автодорога и газопровод со
спецпроходами): загрузите его в веб-интерфейсе или передайте в API/CLI —
расчёт занимает несколько секунд, все точки подключаются.

### REST API

```bash
# 1. Загрузить входной GeoJSON (multipart, до 3 ГБ) и запустить расчёт
curl -F "file=@dataset.geojson" http://localhost:8080/api/v1/tracing/jobs
# -> {"job_id":"<uuid>","status":"QUEUED"}

# 2. Статус
curl http://localhost:8080/api/v1/tracing/jobs/<uuid>

# 3. Результат (GeoJSON, WGS 84)
curl -o result.geojson http://localhost:8080/api/v1/tracing/jobs/<uuid>/result

# 4. Дополнительный режим с учётом глубины (отдельный набор вариантов,
#    depth_start/depth_end, Kгл)
curl -o result-depth.geojson http://localhost:8080/api/v1/tracing/jobs/<uuid>/result-depth

# 5. Пояснительная записка (PDF): карты вариантов, разбивка стоимости,
#    таблицы участков и камер, методика расчёта
curl -o report.pdf http://localhost:8080/api/v1/tracing/jobs/<uuid>/report
```

### Веб-интерфейс (встроен в сервис)

По адресу **http://localhost:8080/ui/** доступен встроенный интерфейс
(офлайн, без CDN — статическая страница внутри jar): загрузка входного
GeoJSON, редактор справочника ограничений (YAML применяется к конкретному
расчёту), интерактивная карта вариантов с атрибутами участков при наведении,
переключение базового режима и режима с глубиной, скачивание всех
артефактов. Формат сервиса при этом не меняется: UI — надстройка над тем же
REST API. Для быстрого показа без Postgres есть демо-профиль:

```bash
java -jar target/heatnet-1.0.0.jar --spring.profiles.active=demo   # встроенная H2
```

### CLI-режим (без БД, для локальной проверки)

```bash
java -jar target/heatnet-1.0.0.jar --spring.profiles.active=cli \
     --input=dataset.geojson --output=result.geojson \
     [--rules=config/rules-example.yml]
```

### Сборка и тесты

```bash
mvn package          # сборка + тесты (JUnit, включая сквозной REST-тест на H2)
mvn package -DskipTests
```

Интеграционный тест `JobApiPostgresIntegrationTest` поднимает настоящий
PostgreSQL через Testcontainers; на машине без Docker он автоматически
пропускается. На очень новых версиях Docker Engine (29+, минимальный API
1.40) клиенту Testcontainers нужно явно указать версию API:

```
mvn package "-DargLine=-Dapi.version=1.44"
```

## Алгоритм

### 1. Разбор входных данных

Потоковый разбор GeoJSON (Jackson streaming) — файл не загружается в память
целиком (требование до 3 ГБ). Каждый объект валидируется: обязательные атрибуты,
типы геометрии; невалидная геометрия чинится (`buffer(0)`) либо возвращается
диагностическая ошибка со списком проблем. Все расчёты — в метрической проекции
EPSG:32637, вход и выход — WGS 84.

### 2. Модель препятствий

Для каждого условного диаметра строится контекст препятствий:

- **Непроходимые** (oks, park, social_area, prohibited_site, water, railway и
  неизвестные типы — консервативно): ядро ⊕ (мин. отступ + полуширина габарита
  пары по таблице 1). Отступ от ОКС зависит от ДУ (5/7/9 м).
- **Специальные проходы** (road, tram_tracks ≥45°, gas_pipeline, power_cable,
  пересечение существующей `heat_network` без врезки): зоны близости с учётом
  собственных габаритов; проход — один прямой участок, границы спецучастка
  (полигон + 3 м / ±2 м вдоль трассы) должны помещаться в одно прямое ребро,
  повороты внутри спецучастка запрещены; наложение зон — максимальный Kспец
  без перемножения.

### 3. Поиск маршрута — граф видимости + A*

Вершины графа — углы раздутых препятствий (буфер со срезанными углами, предел
среза подобран так, чтобы огибание угла не требовало поворота больше 90°).
Ребро допустимо, если не задевает зоны блокировки, корректно пересекает
специальные препятствия и не конфликтует с уже построенными участками новой
сети (пересечение — только в объявленной точке присоединения; параллельное
дублирование трасс ближе 1,5 м запрещено). Вес ребра — прямой вклад в итоговый
показатель S: `0,7·стоимость/25 млн + 0,3·длина/100` с учётом Kспец;
терминальная стоимость кандидата — камера/врезка. A* с мультистартом и
мультицелевым финишем.

### 4. Подход к точке подключения ОКС

Точка подключения лежит внутри полигона ОКС. Строится финальный прямой участок
от границы полигона до точки (отступ к собственному полигону не применяется —
раздел 2.2 техприложения, все компоненты MultiPolygon). Кандидаты узла подхода
перебираются по всем контурам (включая случай точки во внутреннем дворе) и
передаются маршрутизатору мультистартом.

### 5. Точки присоединения

- врезка в существующую камеру (5 млн руб.), если после подключения к ней
  примыкает не более 4 участков (транзитная линия занимает 2 примыкания);
- новая камера в произвольной точке существующего участка (стоимость по
  наибольшему ДУ примыканий, включая разрезаемую линию); точки ближе 10 м
  к доступной существующей камере исключаются — используется камера;
- совместное подключение: врезка в уже построенную новую сеть (новая камера
  в точке ветвления) или в существующий узел новой сети.

Положение врезки в трубу уточняется перпендикуляром из последней вершины
маршрута.

### 6. Сборка сети

Подключения добавляются последовательно (по убыванию расхода). Далее:

- расчёт расходов: сумма `flow_tph` всех ОКС ниже по участку;
- подбор ДУ по таблице 1: пропускная способность + предельная длина по каждому
  непрерывному пути «лист → точка присоединения» (общий участок учитывается
  в каждом пути) + неубывание ДУ к месту присоединения; итеративно до фикс-точки;
- если после подбора ДУ фактический габарит вырос и отступы нарушены — вариант
  перестраивается с увеличенным расчётным габаритом;
- деление рёбер на спецучастки: технические узлы на границах, laying_method
  base/special, стоимость `L · cнов(ДУ) · Kспец` (Kгл = 1 в 2D-режиме);
- камеры в точках ветвления, стоимость по наибольшему ДУ примыканий;
- сводка варианта: construction_cost, штрафы за неподключённые точки
  (100 млн + 500 тыс.·G), calculated_cost, score.

### 7. Варианты, оптимизация и ранжирование

- **v1 shared** — совместное подключение с общими участками. Строится пятью
  детерминированными порядками вставки ОКС (по расходу, от дальних/ближних
  к сети, два перемешивания) — жадная эвристика чувствительна к порядку;
  берётся лучший. Затем 1-opt-улучшение: каждый ОКС по очереди отключается
  и переприкладывается против итоговой сети (ранние ветви строились, когда
  общей сети ещё не было); пробы на копии плана, принимаются только при
  улучшении показателя. На конкурсном наборе даёт −4% score (12,42 → 11,92).
- **v2 independent** — каждый ОКС отдельно к существующей сети (с fallback на
  совместное подключение, если независимый коридор занят);
- **v3 alternative** — совместное подключение с запретом точек присоединения v1.

Дубли отбрасываются, варианты ранжируются по S (rank = 1 — лучший).

### 8. Конфигурируемый справочник ограничений

Правила таблицы 2 встроены в сервис, но справочник расширяется YAML-файлом
без изменения кода (`--rules=...` в CLI, `HEATNET_RULES_FILE` в сервисе,
пример — `config/rules-example.yml`): новые типы ограничений (классы дорог,
метро, водопровод), переопределение отступов и Kспец, отступы, зависящие от
ДУ (как 5/7/9 м у ОКС), поведение для неизвестных типов. Это же делает
алгоритм переносимым на другие ресурсы: для кабельных или водопроводных
сетей меняется справочник, а не движок.

### 9. Пояснительная записка (PDF)

К каждому расчёту автоматически формируется пояснительная записка
(`GET /jobs/{id}/report`, в CLI — файл `*-report.pdf` рядом с результатом):
сводное сравнение вариантов с формулой показателя S, карта каждого варианта
(Java2D, без внешних сервисов), структура стоимости, потабличная разбивка
участков (ДУ, расход, длина, способ прокладки, Kспец, стоимость), камеры,
врезки и методика расчёта. Кириллица — встроенный шрифт DejaVu, документ
воспроизводим в офлайн-контуре.

### 10. Неподключённые ОКС

Если допустимого маршрута нет, частичный результат сохраняется, ОКС попадает в
`unconnected_oks_ids` сводки, к стоимости добавляется штраф. Намеренное
неподключение не используется: маршрут ищется в две фазы (узкий коридор → весь
охват данных).

## Результаты на конкурсном наборе (17 ОКС, 488,7 т/ч)

| Вариант | Стоимость, руб. | Длина, м | Score | Не подключено |
|---|---|---|---|---|
| v1 shared | 242 468 417 | 1 724,1 | 11,96 | — |
| v3 alternative | 253 520 868 | 1 759,9 | 12,38 | — |
| v2 independent | 747 576 028 | 6 413,1 | 40,17 | — |

Полное время расчёта на наборе — **~15 секунд** (ноутбук), включая семь
порядков вставки, 1-opt-оптимизацию и режим с глубиной.

### Масштабируемость (стресс-тест)

Генератор синтетического города (`кварталы с домами, уличная сетка,
магистрали с камерами, река, ж/д, автодороги, газопроводы`) проверяет
устойчивость на городском масштабе:

| Набор | Зданий | ОКС | Время | Результат |
|---|---|---|---|---|
| конкурсный | 85 | 17 | 15 с | все проверки пройдены |
| синтетика ×10 | 1 138 | 150 | 40 с | 150/150, все проверки пройдены |
| синтетика ×30 | 3 156 | 400 | ~6 мин | 400/400; единичные участки помечены как требующие проверки |

Память — до ~2–3 ГБ на ×30. Спецпроходы автодорог (угол ≥ 45°, Kспец 1,6)
и газопроводов проявляются и валидируются именно на стресс-наборах —
в конкурсном наборе special-препятствий нет.

### Производительность

- отступы считаются сразу под консервативный расчётный габарит (ДУ по
  суммарному расходу, не выше ДУ 400) — маршруты не перестраиваются после
  подбора фактических диаметров;
- статическая часть проверки рёбер (препятствия входного набора) кэшируется
  в контексте и переиспользуется всеми ОКС и вариантами; барьеры построенной
  сети проверяются отдельно с посегментным пространственным индексом;
- эвристика A* и свободные вершины графа предвычисляются; дальние кандидаты
  присоединения отсекаются (дальняя врезка не выигрывает по показателю S);
- варианты v1 и v2 строятся параллельно (JTS PreparedGeometry потокобезопасен);
- «независимый» вариант считается в быстром режиме (бюджет раскрытий A* и
  ограничение длины ребра графа с деградацией к точному поиску); основной
  и альтернативный варианты считаются без ограничений — качество лучшего
  варианта не жертвуется скорости.

### Дополнительный режим с учётом глубины

Реализован как отдельный набор вариантов (`GET /jobs/{id}/result-depth`,
в CLI — файл `*-depth.geojson`): вертикальный профиль строится вдоль
2D-маршрутов по условным глубинам техприложения (поверхность горизонтальна,
Z-координаты не требуются). Каждое пересечение задаёт окно допустимых глубин
верха габарита (над газопроводом/кабелем/теплосетью с нормативным просветом
или под ними; под дорогой — не выше 1,0 м, трамваем — 1,2 м); выбирается
вариант с меньшей стоимостью. Переходы — уклон ≤ 0,10 м/м, между близкими
пересечениями изменённая глубина сохраняется, на изломах профиля и отметке
3,0 м создаются технические узлы, заглубление ниже 3,0 м оплачивается
Kгл = 1 + 0,1·(h − 3). Вертикальные параметры настраиваются тем же
YAML-справочником (`vertical:` у типа ограничения).

## Границы применения
- Реконструкция существующей сети не рассчитывается (актуальное техприложение
  и разъяснение №14).
- Неизвестные типы ограничений трактуются консервативно как непроходимые
  с отступом 1 м — сервис не падает на расширенных наборах.
- Совместное подключение строится жадной вставкой (по убыванию расхода) —
  близко к оптимуму Штейнера, но без гарантии глобального оптимума.
