# Heatnet — сервис моделирования трасс подключения к тепловым сетям

Решение конкурсного кейса «Лидеры цифровой трансформации» 2026: сервис принимает
GeoJSON с существующей тепловой сетью, камерами, точками подключения перспективных
ОКС и пространственными ограничениями, автоматически строит совместный и, при наличии
содержательного отличия, альтернативный вариант новой сети и выгружает результат в GeoJSON по разделу 7
технического приложения.

**Адрес стенда:** <https://heatnet.85-198-82-32.nip.io> (веб-интерфейс, Swagger UI,
интерактивный [разбор алгоритма](https://heatnet.85-198-82-32.nip.io/ui/algorithm.html)).
Документация обновлена 19.10.2026. Расчётные показатели ниже подтверждены
эталонной сборкой с SHA-256
`1de15701874e025adbd2a096beff93602d5af6ab317cf68e51d60f93d190da84`.
Текущая сборка выпуска сохраняет её расчётные классы и зависимости; изменены
веб-интерфейс, обработка заданий и конфигурация развёртывания. SHA-256 JAR
проверенного Docker-образа:
`984e6f57e1abadccf5f4c4a7e92d5f3da3d1752e62b628d97062c65cf5dc10b6`.
Ведомость выпуска в рабочей области проекта:
`context/docker-web-release-2026-10-19/release-manifest.json`.
Локальная Docker-проверка не означает публикацию обновления на публичном стенде.
Подробное описание — в [сопроводительной документации](docs/soprovoditelnaya-dokumentaciya.md).

В режиме «С учётом глубины» доступен [продольный профиль выбранного ОКС](docs/longitudinal-profile.md):
глубины и габарит трубы, уклоны, пересечения препятствий и взаимная подсветка
с картой. Профиль читается из сохранённого результата и не меняет расчёт сети.

[Карточка подключения](docs/connection-card.md) работает в обоих режимах:
нагрузка ОКС, врезка, общий и индивидуальный путь, ввод через внешнюю стену,
ДУ и фактическое объяснение маршрута. Выбор ОКС связан с картой и профилем;
сумма стоимостей участков пути отделена от цены индивидуального подключения.

Карточку и профиль можно получить без веб-интерфейса: отдельный
[PDF-паспорт ОКС](docs/connection-card.md#паспорт-подключения-в-pdf) содержит
схему пути, ввод, таблицы участков и объяснения; глубинный вариант добавляет
продольный профиль. Выгрузка доступна через API, CLI и кнопку интерфейса.
Она читает сохранённый результат без повторной трассировки.

Для анализа изменений есть [сравнение двух сохранённых расчётов](docs/scenario-comparison.md)
через API и CLI: стоимость, подключения, изменённые трассы и отдельный PDF/JSON.
В `samples/scenario-comparison/` — пример добавления запретной зоны.

## Стек (по требованиям ТЗ, п. 3.2)

| Компонент | Версия |
|---|---|
| Java | 11 |
| Spring Boot (`spring-boot-starter-parent`) | 2.6.3 |
| СУБД | PostgreSQL (docker-compose: postgres:15) |
| Документация API | springdoc-openapi-ui 1.7.0 (Swagger UI) |
| Развёртывание | docker-compose |
| Геометрия | JTS 1.19, proj4j (WGS 84 ⇄ EPSG:32637) |

PostgreSQL хранит задания расчёта: статусы, время, пути к файлам и сводки.
Геометрия зданий и сетей поступает в GeoJSON; входные и результирующие GeoJSON,
YAML и PDF хранятся файлами в `HEATNET_STORAGE` (по умолчанию `./data`).

## Быстрый старт

### Docker (рекомендуется, Ubuntu Server 22)

```bash
docker compose up --build -d
# Swagger UI: http://localhost:8080/swagger-ui.html
# Веб-интерфейс: http://localhost:8080/ui/
```

Для проверки без конкурсных данных в репозитории лежит синтетический
пример входных данных — `samples/sample-city.geojson` (25 кварталов,
12 точек подключения, река, ж/д, автодорога и газопровод со
спецпроходами): загрузите его в веб-интерфейсе или передайте в API/CLI.

### REST API

```bash
# 1. Загрузить входной GeoJSON (multipart) и запустить расчёт
curl -F "file=@dataset.geojson" http://localhost:8080/api/v1/tracing/jobs
# -> {"job_id":"<uuid>","status":"QUEUED"}

# 2. Статус
curl http://localhost:8080/api/v1/tracing/jobs/<uuid>

# 3. Результат (GeoJSON, WGS 84)
curl -o result.geojson http://localhost:8080/api/v1/tracing/jobs/<uuid>/result

# 4. Дополнительный режим с учётом глубины (отдельный набор вариантов,
#    depth_start/depth_end, Kгл)
curl -o result-depth.geojson http://localhost:8080/api/v1/tracing/jobs/<uuid>/result-depth

# 5. Пояснительная записка (PDF): карты вариантов, разбивка стоимости,
#    таблицы участков и камер, методика расчёта
curl -o report.pdf http://localhost:8080/api/v1/tracing/jobs/<uuid>/report

# 6. Паспорт выбранного ОКС с профилем (n:10 — числовой ID 10)
#    Точные oks_key предварительно получите из /connection?variant_id=d1.
curl -o passport.pdf "http://localhost:8080/api/v1/tracing/jobs/<uuid>/connection.pdf?variant_id=d1&oks_key=n%3A10"
```

Spring принимает GeoJSON до 3 GiB, YAML до 1 MiB, весь multipart-запрос до 3100 MiB;
прокси `deploy/Caddyfile` допускает 4 GB с запасом на YAML и обрамление.
Это параметры приёма, а не доказанная возможность рассчитать любой файл
такого размера. Порт 8080 доступен только на localhost; публичный стенд
использует Caddy. Настройка памяти и выпуска — в [deploy/DEPLOY.md](deploy/DEPLOY.md).

YAML больше 1 MiB отклоняется до создания задания с HTTP 413 (`RULES_TOO_LARGE`).
По умолчанию выполняется один расчёт одновременно, очередь содержит до 100
заданий (`HEATNET_TRACING_WORKERS` / `HEATNET_TRACING_QUEUE_CAPACITY`). При отказе
приёма в очередь API возвращает HTTP 503 (`TRACING_QUEUE_FULL`), сохранённое
задание получает `ERROR`. После перезапуска прежние `QUEUED`/`RUNNING`
переводятся в `ERROR` с объяснением; для расчёта нужно отправить данные заново.
Завершённые задания и файлы сохраняются в томах. Поддерживается один экземпляр
приложения: несколько реплик с общей БД запускать нельзя.

Статус задания содержит `diagnostics` и признаки доступности
`result_available`, `depth_available`, `report_available`. Каждая причина
содержит `variant_id`, `mode` (`base`/`depth`), `code`, `message` и
`segment_ids` — идентификаторы участков исключённого варианта.

| Результат проверки | Статус задания и доступные файлы |
|---|---|
| Все рассчитанные базовые варианты недопустимы | `ERROR`; выгрузки возвращают HTTP 409 с кодом `NO_VALID_BASE_VARIANT`, сообщением и диагностикой |
| Есть допустимый базовый вариант, но нет глубинных | `DONE`; базовый GeoJSON и PDF доступны, `/result-depth` возвращает HTTP 409 `DEPTH_RESULT_UNAVAILABLE` |
| Исключена только часть вариантов | `DONE`; файлы содержат оставшиеся варианты и причины исключения остальных |

Отказ означает, что проверку не прошли рассчитанные варианты; он не доказывает
отсутствие допустимого решения. Неподключённые ОКС в допустимой частичной сети
учитываются отдельно через `unconnected_oks_ids` и штрафы.

Причины сохраняются рядом с результатом в `*-diagnostics.json`, добавляются
в поле `diagnostics` верхнего уровня GeoJSON при непустом списке и в PDF.
У результата без замечаний формат GeoJSON сохраняется.

### Веб-интерфейс (встроен в сервис)

По адресу **http://localhost:8080/ui/** доступен встроенный интерфейс
(статическая страница внутри JAR, без CDN-зависимостей): загрузка входного
GeoJSON и YAML, редактор справочника ограничений (YAML применяется к конкретному
расчёту), интерактивная карта вариантов с атрибутами участков при наведении,
переключение базового режима и режима с глубиной, скачивание всех
артефактов. Формат сервиса при этом не меняется: UI — надстройка над тем же
REST API. Тайлы подложки OpenStreetMap загружаются из интернета; они не
используются движком как данные уличных коридоров. Для быстрого показа без
Postgres есть демо-профиль:

```bash
java -jar target/heatnet-1.0.0.jar --spring.profiles.active=demo   # встроенная H2
```

### CLI-режим (без БД, для локальной проверки)

```bash
java -jar target/heatnet-1.0.0.jar --spring.profiles.active=cli \
     --input=samples/sample-city.geojson --output=result.geojson
```

Для собственного справочника добавьте `--rules=config/rules-example.yml`;
без этого параметра применяются встроенные правила.

Для отдельного PDF-паспорта по **уже сохранённому** результату:

```bash
java -jar target/heatnet-1.0.0.jar --spring.profiles.active=cli --export-connection \
     --input=dataset.geojson --result=result-depth.geojson \
     --variant=d1 --oks-key=n:10 --output=passport.pdf
```

Нужны исходный GeoJSON и результат одного расчёта; при использовании
переопределений передайте тот же `--rules=rules.yml`. Для паспорта без глубин
укажите `--result=result.geojson --variant=v1`. Сервер и БД не требуются;
новый расчёт не выполняется. Ключ `n:10` обозначает числовой ID, `s:10` —
строковый. Подробнее — [экспорт паспорта](docs/connection-card.md).

Два готовых расчёта можно сравнить без сервера и БД:

```bash
java -jar target/heatnet-1.0.0.jar --spring.profiles.active=cli --compare-results \
     --before-input=before.geojson --before-result=before-result.geojson --before-variant=v1 \
     --after-input=after.geojson --after-result=after-result.geojson --after-variant=v1 \
     --output=comparison.json
```

Рядом создаётся `comparison.pdf`. Для каждого расчёта отдельно передайте его
YAML через `--before-rules` / `--after-rules`, если использовались переопределения.
Для глубинного сравнения нужны два depth-результата и варианты `d1`/`d3`.
API и воспроизводимый пример — в [инструкции сравнения](docs/scenario-comparison.md).

CLI возвращает код `0`, если есть допустимый базовый результат, `3` — если
все рассчитанные базовые варианты исключены, `2` — если не указаны вход/выход.
Ошибочный GeoJSON или YAML завершает CLI с кодом `1` до расчёта.
Рядом с `result.geojson` записывается `result-diagnostics.json`. При полном
отказе GeoJSON/PDF не выдаются; при отказе только глубины отсутствует
`result-depth.geojson`. Старые файлы именно этих выходов удаляются, чтобы
повторный запуск не оставлял прежний результат под видом нового.

## Алгоритм

### 1. Разбор входных данных

Потоковый разбор GeoJSON (Jackson streaming) — исходный текст файла не
загружается в память целиком; геометрия и расчётные индексы хранятся в памяти.
Каждый объект валидируется: обязательные атрибуты,
типы геометрии; невалидная геометрия чинится (`buffer(0)`) либо возвращается
диагностическая ошибка со списком проблем. Все расчёты — в метрической проекции
EPSG:32637, вход и выход — WGS 84.

Поддерживаемая область входных чисел и идентификаторов:

- `heat_network.diameter` — целое число от 1 до 1400. Для промежуточного
  существующего ДУ расчётный габарит выбирается вверх по таблице, как раньше;
  дробь, ноль, отрицательное число и неподдерживаемый ДУ отклоняются без усечения.
- `oks_connection_point.flow_tph` — конечное неотрицательное число; нулевая
  нагрузка остаётся самостоятельной целью. Числа, исчезающие при переводе в
  `double`, переполнение нагрузки или суммы возможных штрафов отклоняются.
  Нагрузка выше 22 501,9 т/ч допустима во входе, но такой ОКС остаётся
  неподключённым со штатным штрафом: подходящего нового ДУ в таблице нет.
- `id` — строка или точное JSON-число, уникальное во всём входном наборе.
  Числа `1`, `1.0`, `1e0` обозначают один ID; строка `"1"` — другой.
  При повторе ошибка указывает обе позиции `features[...]`. Большие целые
  и точные десятичные ID сохраняются числами в серверной выгрузке. Новые
  идентификаторы не занимают имена исходных объектов.

Это правила поддерживаемого входа сервиса; глобальная уникальность и диапазон
существующего ДУ не выдаются за дополнительные дословные нормы организаторов.
Ошибочный GeoJSON останавливается до запуска движка; API сохраняет обычный
жизненный цикл `POST 202 → ERROR` с объяснением поля, CLI завершается с ошибкой.
Финальная проверка не допускает выдачу участка с недостаточной пропускной
способностью или превышением непрерывной длины выбранного ДУ. Когда общей
ветви недостаточно, поиск рассматривает раздельные присоединения к исходной сети.

При дорисовке препятствий интерфейс сохраняет исходный текст GeoJSON и добавляет
только новые объекты: браузер не пересериализует исходные ID и нагрузки через
JavaScript Number. Подписи очень больших числовых ID на карте всё ещё ограничены
точностью Number; скачиваемый файл и серверный расчёт сохраняют точные ID.

### 2. Модель препятствий

Для каждого условного диаметра строится контекст препятствий:

- **Непроходимые** (oks, park, social_area, prohibited_site, water, railway и
  неизвестные типы — консервативно): ядро ⊕ (мин. отступ + полуширина габарита
  пары по таблице 1). Отступ от ОКС зависит от ДУ (5/7/9 м).
- **Специальные проходы** (road, tram_tracks ≥45°, gas_pipeline, power_cable,
  пересечение существующей `heat_network` без врезки): зоны близости с учётом
  собственных габаритов; проход — один прямой участок, границы спецучастка
  (для полигона — по 3 м за границей с каждой стороны вдоль трассы;
  для линейного объекта — ±2 м от пересечения) должны помещаться в одно прямое ребро,
  повороты внутри спецучастка запрещены; наложение зон — максимальный Kспец
  без перемножения. Вне специального участка сохраняется отступ по ДУ;
  контакт с полигоном не освобождает от него всю зону близости. Для камеры
  на исходной теплосети внутри дороги/трамвая запас нужен только со стороны выхода.

### 3. Поиск маршрута — граф видимости + A*

Вершины графа — углы раздутых препятствий (буфер со срезанными углами, предел
среза подобран так, чтобы огибание угла не требовало поворота больше 90°).
Ребро допустимо, если не задевает зоны блокировки, корректно пересекает
специальные препятствия и не конфликтует с уже построенными участками новой
сети (пересечение — только в объявленной точке присоединения; параллельное
дублирование трасс ближе 1,5 м запрещено). Вес ребра — прямой вклад в итоговый
показатель S: `0,7·стоимость/25 млн + 0,3·длина/100` с учётом Kспец;
терминальная стоимость кандидата — камера/врезка. A* с мультистартом и
мультицелевым финишем.

### 4. Подход к точке подключения ОКС

Точка подключения лежит внутри полигона ОКС. Строится финальный прямой участок
от границы полигона до точки (отступ к собственному полигону не применяется —
раздел 2.2 техприложения, все компоненты MultiPolygon). Кандидаты узла подхода
перебираются по всем контурам (включая случай точки во внутреннем дворе) и
передаются маршрутизатору мультистартом. До финального ввода маршрут не может
повторно проходить через собственное здание. Рассматриваются нормальные подходы
к стенам, включая прямое присоединение к построенной сети. В локальном улучшении
проверяются до трёх близких нормальных вводов в пределах +1 м от кратчайшего
допустимого: это ограничение дополнительных проб, а не норма ТЗ. Другой ввод
принимается при сохранении подключений, допустимости полной сети, уменьшении S
и отсутствии роста полной стоимости. Для зависимых ветвей предусмотрена
ограниченная совместная перестройка. Глобальный оптимум стены не гарантируется.

### 5. Точки присоединения

- врезка в существующую камеру (5 млн руб.), если после подключения к ней
  примыкает не более 4 участков (транзитная линия занимает 2 примыкания);
- новая камера в произвольной точке существующего участка (стоимость по
  наибольшему ДУ примыканий, включая разрезаемую линию); точки на расстоянии ≤10 м
  к доступной существующей камере исключаются — используется камера;
- совместное подключение: врезка в уже построенную новую сеть (новая камера
  в точке ветвления) или в существующий узел новой сети.

Положение врезки в трубу уточняется перпендикуляром из последней вершины
маршрута.

### 6. Сборка сети

Подключения добавляются последовательно (по убыванию расхода). Далее:

- расчёт расходов: сумма `flow_tph` всех ОКС ниже по участку;
- подбор ДУ по таблице 1: пропускная способность + предельная длина по каждому
  непрерывному пути «лист → точка присоединения» (общий участок учитывается
  в каждом пути) + неубывание ДУ к месту присоединения; итеративно до фикс-точки;
- если после подбора ДУ фактический габарит вырос и отступы нарушены — вариант
  перестраивается с увеличенным расчётным габаритом;
- деление рёбер на спецучастки: технические узлы на границах, laying_method
  base/special, стоимость `L · cнов(ДУ) · Kспец` (Kгл = 1 в 2D-режиме);
- камеры в точках ветвления, стоимость по наибольшему ДУ примыканий;
- сводка варианта: construction_cost, штрафы за неподключённые точки
  (100 млн + 500 тыс.·G), calculated_cost, score.

### 7. Варианты, оптимизация и ранжирование

- **v1 shared** — совместное подключение с общими участками. Строится семью
  детерминированными порядками вставки ОКС (по расходу, от дальних/ближних
  к сети, четыре перемешивания) — жадная эвристика чувствительна к порядку;
  берётся лучший. Затем 1-opt-улучшение: каждый ОКС по очереди отключается
  и переприкладывается против итоговой сети (ранние ветви строились, когда
  общей сети ещё не было); пробы на копии плана, принимаются только при
  улучшении показателя с проверкой допустимости и полноты подключения.
- **v3 alternative** — совместное подключение с запретом точек присоединения v1.

Дубли и недопустимые варианты отбрасываются; при успешном расчёте выдаётся
один или два базовых варианта. Они ранжируются по S
(rank = 1 — лучший). Идентификатор стратегии не равен месту: v3 может иметь
rank 1 или 2. В режиме глубины соответствующие идентификаторы — d1 и d3.
Глубинные варианты проверяются отдельно: допустимость исходных окон глубины,
минимальное покрытие и уклон построенного профиля. Исключение d3 не удаляет
допустимый v3 или d1; ранги оставшихся вариантов пересчитываются без смены ID.
Это не подтверждение всех вертикальных нормативных условий на любых данных.
Раздельный **v2 independent** в основном расчёте не запускается: его стратегия
сохранена внутри планировщика для диагностики, старые выгрузки поддерживаются.

### 8. Конфигурируемый справочник ограничений

Правила таблицы 2 встроены в сервис, но справочник расширяется YAML-файлом
без изменения кода (`--rules=...` в CLI, `HEATNET_RULES_FILE` в сервисе,
пример — `config/rules-example.yml`): новые типы ограничений (классы дорог,
метро, водопровод), переопределение отступов и Kспец, отступы, зависящие от
ДУ (как 5/7/9 м у ОКС), поведение для неизвестных типов. Применение движка к
другим ресурсам потребует адаптации расчётной модели, таблиц и проверок;
готовая поддержка проектирования водопровода или кабельной сети не заявляется.

`min_distance_by_du` действует и для запрещённых, и для специальных препятствий,
включая `heat_network_crossing`. Порог выбирается по ДУ **новой** трубы:
используется первая подходящая граница `max_du` включительно, выше последней —
последнее значение. К отступу добавляются расчётные габариты; у существующей
теплосети собственный габарит берётся по её ДУ. Таблица имеет приоритет перед
`min_distance`; отдельное последующее переопределение `min_distance` без таблицы
заменяет унаследованные пороги постоянным отступом. `special_margin` задаёт
границы спецучастка и не заменяет горизонтальный отступ.

При `k_spec: 1` пересечение сохраняет способ прокладки `special`, геометрические
и вертикальные условия. Надбавка Kспец в этом случае отсутствует; надбавка за
глубину рассчитывается отдельно. На перекрытиях используется максимальный Kспец,
а длина специального прохода учитывается без двойного счёта.

YAML проверяется до запуска расчёта. Горизонтальные размеры и отступы должны
быть конечными неотрицательными числами, `k_spec` — не меньше 1, `min_angle` —
от 0 до 90 включительно. Числа в кавычках, `null`, неизвестные имена полей,
повторные ключи и несколько YAML-документов в одном файле отклоняются.
Имена новых типов ограничений остаются свободными. Это правила формата
расширения сервиса; встроенные нормы таблицы 2 не меняются.

В `min_distance_by_du` поле `distance` обязательно; `max_du` — положительное
целое до 2147483647 либо отсутствует для открытого диапазона. Повторяющиеся
границы запрещены, порядок строк свободный. Пустой список `[]` удаляет
унаследованные пороги и возвращает постоянный отступ `min_distance`.
В секции `heat_network_crossing` поддерживается только `mode: special`;
`min_angle` и `own_half_width` должны отсутствовать или равняться 0, поскольку
для исходной теплосети угол не ограничивается, а габарит определяется по её ДУ.
При ошибке CLI завершается с причиной; загруженная через API задача получает
статус `ERROR`, расчётные файлы не создаются. Ошибки параметров содержат имя
поля; ошибки синтаксиса сообщает YAML-парсер с доступной позицией или ключом.

### 9. Пояснительная записка (PDF)

К каждому расчёту автоматически формируется пояснительная записка
(`GET /api/v1/tracing/jobs/{id}/report`, в CLI — файл `*-report.pdf` рядом с результатом):
сводное сравнение вариантов с формулой показателя S, карта каждого варианта
(Java2D, без внешних сервисов), структура стоимости, потабличная разбивка
участков (ДУ, расход, длина, способ прокладки, Kспец, стоимость), камеры,
врезки и методика расчёта. Кириллица — встроенный шрифт DejaVu, документ
воспроизводим в офлайн-контуре.

### 10. Неподключённые ОКС

Если допустимый маршрут не найден, частичный результат сохраняется, ОКС попадает в
`unconnected_oks_ids` сводки, к стоимости добавляется штраф. Намеренное
неподключение не используется: маршрут ищется в две фазы (узкий коридор → весь
охват данных).

### Производительность

- отступы считаются сразу под консервативный расчётный габарит (ДУ по
  суммарному расходу, первоначально не выше ДУ 400); если фактический ДУ
  нарушает отступы, выполняется повторное построение с большим габаритом;
- статическая часть проверки рёбер (препятствия входного набора) кэшируется
  в контексте и переиспользуется всеми ОКС и вариантами; барьеры построенной
  сети проверяются отдельно с посегментным пространственным индексом;
- внутри одного поиска A* каждая неориентированная пара узлов проверяется
  не более одного раза; дополнительная локальная таблица результатов удалена,
  общий кеш статических препятствий сохранён;
- эвристика A* и свободные вершины графа предвычисляются; дальние кандидаты
  присоединения отсекаются (дальняя врезка не выигрывает по показателю S);
- семь порядков построения shared считаются параллельно, затем выполняются
  локальное улучшение лучшего и построение alternative;
- independent исключён из основного расчёта: нет фонового построения или
  ожидания этого варианта. Бюджеты поиска shared/alternative не изменены.

### Дополнительный режим с учётом глубины

Реализован как отдельный набор вариантов (`GET /api/v1/tracing/jobs/{id}/result-depth`,
в CLI — файл `*-depth.geojson`): вертикальный профиль строится вдоль
2D-маршрутов по условным глубинам техприложения (поверхность горизонтальна,
Z-координаты не требуются). Каждое пересечение задаёт окно допустимых глубин
верха габарита (над газопроводом/кабелем/теплосетью с нормативным просветом
или под ними; под дорогой — не выше 1,0 м, трамваем — 1,2 м).
Сначала пробуется проход сверху. Если его нельзя согласовать с уклоном и
соседними участками, проверяется разрешённый проход снизу для конкретного
пересечения. Переходы — уклон ≤ 0,10 м/м, между близкими
пересечениями изменённая глубина сохраняется, на изломах профиля и отметке
3,0 м создаются технические узлы, заглубление ниже 3,0 м оплачивается
Kгл = 1 + 0,1·(h − 3). Вертикальные параметры настраиваются тем же
YAML-справочником (`vertical:` у типа ограничения). Частичное переопределение
сохраняет остальные параметры; `unknown_default.vertical` применяется к
неизвестным типам. `crossing` принимает `under` или `above_or_below`;
числовые вертикальные поля должны быть конечными неотрицательными числами
(числа в кавычках не принимаются). Неверное значение останавливает загрузку
с указанием правила и поля; синтаксические ошибки YAML сообщает парсер.
`heat_network_crossing.vertical.obstacle_top_depth` задаёт единую условную
глубину верха расчётного габарита всей исходной теплосети: она применяется
к пересечениям и отметкам врезок через существующие камеры или новые камеры
на исходных трубах. По умолчанию это 3,0 м по техприложению; изменение через
YAML — расширение модели сервиса. Значение сохраняется при экспорте YAML
и для `crossing: under`, где `min_top_depth` отдельно задаёт условие прохода.
Предел уклона 0,10, минимум покрытия 0,70, обычная глубина новой сети 3,0 м
и порог формулы Kгл 3,0 м не переопределяются. Если заданная глубина врезки
меньше 0,7 м, глубинный вариант исключается с объяснением конфликта покрытия;
допустимый базовый 2D-результат сохраняется.

Профили согласуются через общие узлы: рампа может начинаться до новой камеры
на соседнем ребре; отметки врезок соответствуют заданной глубине исходной сети.
В этой условной модели в узле присоединения совмещаются глубины верхних
расчётных габаритов; индивидуальные высотные отметки исходных труб не задаются.
Допустимые прежние профили сохраняются. Для проблемной компоненты ограничения
распространяются по графу границ окон и узлов сети; проверяются исходные окна,
покрытие ≥ 0,7 м, уклон и непрерывность. Перебор сторон ограничен 256 наборами
на компоненту. При конфликте или исчерпании поиска вариант исключается с
диагностикой; глобальный оптимум стоимости или полнота поиска не гарантируются.

## Границы применения

- Реконструкция существующей сети не рассчитывается (актуальное техприложение
  и разъяснение №14); вместо гидравлического расчёта используются таблицы
  пропускных способностей и предельных длин.
- Неизвестные типы ограничений трактуются консервативно как непроходимые
  с отступом 1 м; их правила можно настроить через `unknown_default`.
- Совместное подключение использует несколько порядков жадной вставки и
  локальные перестройки. Глобальный оптимум и близость к нему не доказаны.
- Направление трасс вдоль уличных коридоров по слоям OSM остаётся дорожной
  картой. Сейчас дороги из GeoJSON служат ограничениями/спецпроходами,
  а OpenStreetMap в интерфейсе — только подложкой.
- Синтетические 150/400 ОКС не доказывают расчёт всей Москвы, обработку
  произвольного входа 3 ГБ или работу 50 одновременных пользователей.
- Дополнительные адресные проверки касаний вершин полигонов и разрезов
  перекрывающихся спецпроходов с одинаковым Kспец отложены. Это предел
  проверки, а не подтверждённое нарушение конкурсного результата.
- Глубинный режим использует условную горизонтальную поверхность и
  заданные глубины коммуникаций; он не выбирает новую XY-трассу по глубине.
  Полная нормативная сертификация не заявляется.
